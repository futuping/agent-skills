# 任务记录与交接

已有项目工件可承载这些信息时，直接更新它；没有合适位置才新建工作记录。以下是可裁剪模板，不要求填写与任务无关的栏目。

```markdown
# 功能或缺陷
状态：调查 / 实施 / 验证 / 审查 / 已交付
工作位置：仓库、分支/worktree、适用的 commit

## 目标与约束
- 用户目标：
- 不做：
- 约束及已授权交付动作：

## 验收与依据
- [ ] 可观察行为；必要边界；预期结果的独立依据

## 事实、决定与未知
- 相关文件/调用或数据路径：
- 重要决定及原因：
- 假设、小实验和结果：

## 短计划
- [ ] 可验证行为 → 对应验收 → 检查

## 实际证据
- 验收/检查：实际命令或操作；结果；日志/截图/产物位置
- 既有失败、本次失败、未运行项及原因：

## 审查与交付
- 范围：基线...目标；是否包含暂存、未暂存、未跟踪文件
- 发现、核实与处理：
- 运行/使用：
- 发布状态及必要回滚路径：
- done / next / blockers / evidence：
```

## 新上下文只读审查

交给审查者项目规则、任务工件与精确差异范围。要求：

- 只审查、不改文件、不提交、不发远端评论；需要实际检查时保留此边界。
- 自己读取需求和 diff，不仅采信实施者的完成描述。
- 先检查验收覆盖与无关扩展，再找错误行为、回归、数据边界、兼容性和关键验证缺口。
- 每条发现给位置、触发条件、影响、依据与建议验证；无实质发现则说明未验证范围。

主写者核实发现再修复；审查结论不等于正确性保证。

## 跨会话或跨工具

显式传入工件位置、仓库/分支/worktree/commit、已改内容、真实检查结果与下一项。接续者先核对文件和 Git 状态；发现与记录不一致时更新事实，再推进。不要依赖工作文件会被自动读取，也不重复已经有充分证据的已完成工作。
