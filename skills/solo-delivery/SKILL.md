# Solo Delivery

将已授权的软件需求推进到可运行、可检查、可接续的成果。此技能是个人开发流程的综合，按任务裁剪；它不替代项目指令、用户决定、现有权限或显式选定的其他工作流。

## 确定路径

- 先读适用指令、README、依赖清单与锁文件、构建/CI、环境配置和 Git 状态。确认实际根目录、已有修改、运行命令与已知失败；继承用户的 Nix 等环境政策。
- 选用当前任务确实需要且可用的领域技能/工具；用户点名的技能优先。领域技能补专业知识，完整流程框架通常选一套，避免同时控制同一任务。
- 简单且明确的修改直接调查相关点、修改、验证；不强建规格文档、子代理团队或实现镜像测试。
- 中等以上任务先沿用项目已有 issue、规格或任务记录；没有合适位置时才用 `docs/work/<slug>.md`。只维护一份任务事实源，模板见 [任务记录与交接](references/work-record.md)。

## 推进一个可验证单元

1. **目标与事实。** 写清目标、非目标、约束和可观察验收。验收与测试预期来自用户需求、协议、已知正确样例或独立依据，不能由新实现自行定义正确。只集中询问会实质改变结果、兼容性或授权边界的未知；已清楚的范围持续完成。
2. **研究与计划。** 复杂旧代码追踪相关入口、调用与数据流，注明文件位置，区分事实与假设。关键未知先用小实验或最小纵向切片验证，再扩展方案。短计划按可验证行为划分，每项关联验收和检查；不要用计划拖延已明确的小任务。
3. **实施与诊断。** 一次一个行为单元，同一工作树保持一个主写者。行为缺陷先复现，关键逻辑适合失败测试→最小实现；低影响改动使用相称检查。保持项目风格、依赖管理与版本约束，必要依赖变更按既有流程最小更新。相同失败重复且无新证据时，转向复现、日志、假设或环境诊断，再继续；不要猜测式循环。
4. **验证。** 运行受影响的项目检查，再实际走原用户路径。记录命令/操作、结果与证据位置；区分既有失败、本次回归和未运行项。不得通过删检查、重算实现作为期望值或悄悄放宽验收自证通过。按改动选择 [验证与审查](references/verification.md) 中相关分支，不运行无关整套检查。
5. **独立审查。** 中等以上或高影响改动交给新上下文审查者；给需求、约束、精确基线/目标及未提交差异范围。先查规格遗漏/越界，再查缺陷、项目约定与必要设计质量。审查者只报告；主写者核实并定点修复，重跑受影响检查。不要假设同名 review 技能都只读：先读其实际行为。没有独立审查能力时明确说明，仍完成可做的自查与验证。
6. **交付与接续。** 检查最终 diff、必要文档和运行方式，更新完成项、下一步、阻塞与证据。按已有授权完成提交、PR 或具体发布；确需新决定时先准备可审阅结果，避免重复确认已授权动作。准确区分本地可交付、已提交、已推送、已上线；发布后验证目标环境，需要时给回滚路径。

## 保持流程轻量

- 并行调查或审查可以分工；并行写入先隔离工作树、任务边界和整合责任。切换工具时传任务记录、Git 位置和证据，不只传聊天摘要。
- 当问题源于工具、环境或上下文时，先修对应缺口，不默认加长提示词。
- 仅在维护工作属于授权范围时，把反复有效的事实或流程写回其单一源码；删除过时或没有收益的指令。一次任务的偶发细节不升级成全局规则。
- 开发 AI 行为、提示词或技能时，以代表任务、正负触发和端到端结果比较修改前后；普通软件任务不强制增加评测基础设施。
